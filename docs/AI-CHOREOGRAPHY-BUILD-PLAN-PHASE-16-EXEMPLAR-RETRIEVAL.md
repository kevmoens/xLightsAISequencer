# Build Plan: Phase 16 — Exemplar Retrieval Quality (section-kind bug, descriptions, richer matching)

**Status:** designed (4 design decisions confirmed with the user 2026-10-31), not yet implemented.
Written after a real-data investigation into why generated shows "feel the same" across songs. Must
land before Phase 17 (corpus expansion) does its mining work, so the expanded corpus is built once
against a corrected/richer schema rather than mined twice.

---

## 1. Why this phase exists

### 1a. The real numbers, checked against the live index

`%AppData%\XlightsAI.Studio\corpus-knowledge\exemplar-index.json` (built from the current 6-song
corpus subset) has exactly **181 entries**, distributed across `SectionKind` as:

| Section kind | Count |
|---|---:|
| Chorus | 144 |
| Bridge | 17 |
| Verse | 8 |
| Unknown | 9 |
| Intro | 2 |
| Outro | 1 |
| PreChorus | **0** |
| Solo | **0** |

80% of all real exemplar material is Chorus, drawn mostly from just 2 of the 6 source songs.

### 1b. A real bug found while investigating, not just thin data

`DirectorPromptBuilder.cs` queries `knowledge.Exemplars.FindSimilar(query, ExemplarsPerSectionKind)`
once per `SectionKind`, with `query.SectionKind` set to the kind it wants an example of. But
`ExemplarIndex.FindSimilar` (`src/XlightsAI.Studio.Pipeline/ExemplarIndex.cs`) never filters by section
kind at all — it ranks every entry in the whole index by cosine similarity over
`ExemplarFingerprint.ToComparisonVector()`, which is **only two numbers**: normalized tempo and energy
percentile (`src/XlightsAI.Studio.Pipeline/ExemplarFingerprint.cs`). `DirectorPromptBuilder` then prints
the result labelled with the *query's* kind, not the retrieved entry's real kind:

```csharp
sb.AppendLine($"- [{kind}] \"{exemplar.Fingerprint.SongTitle}\" bars {exemplar.Fingerprint.StartBarIndex}-{exemplar.Fingerprint.EndBarIndexExclusive}, ...");
```

Net effect: a Solo or PreChorus query — kinds with **zero** real entries — still confidently returns
some Chorus snippet and tells the Director "here's a Solo example." This is actively misleading, not
merely a missing-data gap.

### 1c. Two fields already in the schema do nothing today

`ExemplarFingerprint.BandBalance` and `.VocalActivityHint` exist but are always `null` — confirmed
against real stored entries. `ToComparisonVector`'s own doc comment says as much: *"Band balance/vocal
activity are omitted (both null for every real exemplar today); extending this vector once Phase 3
supplies them is the natural place to do it, not fabricating zeros for an unmeasured dimension today."*
`ExemplarIndexBuilder` (`src/XlightsAI.Studio.Pipeline/ExemplarIndexBuilder.cs`) never computes or
populates them when building an entry — the corpus-mining pipeline today only runs tempo/beat/
section/phrase analysis per song, not band-energy/vocal-activity analysis.

### 1d. No human- or AI-readable "when to use this" text exists at all

An entry today carries only: `SongTitle`, `Provenance`, a bar range, `TempoBpm`, `EnergyPercentile`,
`SectionKind`, the two always-null fields above, and the actual placed `Effects`. There is nothing
describing *why* this snippet is a good example, or what about the target song should make the Director
reach for it.

---

## 2. Proposed technical changes

Four design decisions were made with the user, in order; each subsection is one of them.

### 2a. Decision: filter to exact kind first, fall back to nearest kind — but always disclosed

`ExemplarIndex.FindSimilar` must filter candidates to `entry.Fingerprint.SectionKind == query.SectionKind`
first. Only when **zero** entries of that exact kind exist does it fall back to the nearest entry by
tempo/energy similarity from a different kind — and that fallback must be visibly, honestly labelled in
the prompt text itself (e.g. `[Solo — no real Solo example exists, nearest available: Chorus]`), never
silently presented as if it were a real Solo example. `DirectorPromptBuilder`'s print line changes from
printing the query's kind unconditionally to printing the entry's own real kind, with the fallback
caveat appended only when a fallback actually happened.

### 2b. Decision: real LLM call per entry for descriptions

Each `ExemplarEntry` gains a description field, generated by a real model call per entry (from its
placed `Effects`, bar range, tempo, energy percentile, and section kind) rather than a cheap
deterministic template — richer, more useful text for the Director at generation time, at the cost of
real API calls scaling with corpus size. Needs a batching/cost plan once Phase 17's larger mining run is
scoped (likely hundreds to low thousands of entries once Phase 17 lands) — not yet designed.

### 2c. Decision: populate `BandBalance`/`VocalActivityHint` for real

Corpus mining gains the band-energy/vocal-activity analysis stages (the same analyzers
`AudioAnalysisRunner` already runs for real generation) so these two fields stop being permanently
`null`, and `ExemplarFingerprint.ToComparisonVector()` is extended to actually use them alongside
tempo/energy. Because this decision was made *before* Phase 17 runs its mining pass, Phase 17's mining
work does the heavier analysis once per song rather than needing a second pass later.

### 2d. Decision: `ExemplarsPerSectionKind` scales with available material

Replace the fixed `DirectorPromptBuilder.ExemplarsPerSectionKind = 2` constant with a per-kind count
that scales with how much real material exists for that kind (e.g. more shown for Chorus once the
corpus is Chorus-heavy, fewer for thinner kinds), capped at a reasonable maximum so the stable prefix
doesn't grow unboundedly as Phase 17 adds more songs. Exact scaling curve/cap not yet designed.

---

## 3. Sequencing

Must land before Phase 17's mining work so the expanded corpus (dozens more real songs, Phase 17 §1)
gets mined once against the corrected retrieval logic and final schema, not twice — in particular,
2c's decision (populate real band-balance/vocal-activity) is exactly why Phase 17 should wait: mining
now already includes the heavier analysis stages Phase 17 will need anyway.

## 4. Acceptance criteria

- A query for a `SectionKind` with zero real exemplars either returns nothing, or returns a different
  kind's entry with an explicit, visible fallback disclosure in the prompt text — never a silent
  mislabel.
- Every exemplar entry (181 existing + whatever Phase 17 adds) carries a real, model-written
  description.
- `ExemplarFingerprint.BandBalance`/`VocalActivityHint` are populated with real analysis output for
  every newly mined entry, and actually participate in `FindSimilar`'s similarity ranking.
- `ExemplarsPerSectionKind` is no longer a single fixed constant — the count shown per kind visibly
  varies based on how much real material exists for it.
