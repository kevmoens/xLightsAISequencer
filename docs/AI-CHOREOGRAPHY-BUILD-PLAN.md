# Build Plan: LLM-Driven Choreography

Phase and task breakdown for implementing `docs/AI-CHOREOGRAPHY-ARCHITECTURE.md`. Read that document
first — this one assumes it and doesn't re-derive the reasoning, only the sequencing.

Each phase lists: **why it's sequenced here**, **tasks**, **depends on**, and **acceptance criteria**
(how we know the phase is actually done, not just coded). Phases are ordered by real dependency, not
by estimated effort — some phases are small and fast, some are large, but a later phase will fail or
produce nothing useful if an earlier one isn't solid.

---

## Phase 0 — De-risk: render automation spike + exporter ground truth

**Why first.** Two things could invalidate large parts of the architecture, and both are cheap to
test and expensive to discover late: (1) if `.xsq` files generated by this app can't be opened by a
real xLights install, nothing downstream matters; (2) if headless render automation isn't viable, the
entire L5/L6 critique loop (§9 of the architecture doc) needs a fallback design before Phase 5+ is
built around it. Both are spikes, not features — timebox them and come back with a yes/no answer, not
a perfect implementation.

### Tasks

1. **Capture a real golden fixture.** Open xLights, build a trivial 2-model, 3-effect sequence by
   hand (or import the existing `golden-three-effect-sequence.xsq` fixture's intent), save it, and
   diff the saved XML against what `XsqExporter` currently produces. This directly confirms or
   refutes every defect listed in architecture §12 blocker 4 (`FixedPointTiming`, `type="modelGroup"`,
   missing head fields, `selected` emission, frame rate).
2. **Fix the confirmed exporter defects** from that diff — this is a small, mechanical, high-value
   fix independent of everything else in this plan. Update
   `tests/XlightsAI.Studio.Xlights.Tests/Fixtures/golden/golden-three-effect-sequence.xsq` to match
   real xLights output.
3. **Round-trip test**: export a hand-built `SequenceDocument` with the fixed exporter, open the
   result in a real xLights install, confirm it imports without error or repair-on-load.
4. **Spike `xlDo.exe`**: determine what automation surface it actually exposes (render-to-FSEQ
   headless? screenshot/preview capture? requires a running GUI session?). Document findings — don't
   build on it yet.
5. **Spike the existing render adapter** in `XlightsAI.Studio.Rendering` — read what capability probe
   exists already and what it reports on this machine.
6. **Decide and document the L5 rendering strategy**: real headless render (preferred), GUI-driven
   automation (fallback), or `.xsq`-derived prediction only (last resort, flagged as materially
   weaker per architecture §9). This decision gates how Phase 7 is scoped.

### Depends on
Nothing. Can start immediately.

### Acceptance criteria
- A real xLights install opens an app-exported `.xsq` with zero errors/repairs.
- The golden fixture matches real xLights output byte-for-byte on the covered fields.
- A written yes/no answer, with evidence, on whether headless rendering is achievable — this
  determines whether Phase 7 builds the full critique loop or the degraded fallback.

## Phase 1 — Foundation: geometry, recipe system, and the IR

**Why next.** Three blockers from architecture §12 (items 1–3) sit underneath everything else
regardless of what Phase 0 finds about rendering. Pixel-weighted coverage (the single most important
correctness mechanism in the whole design) is impossible without real geometry. The effect-recipe
system can't carry a palette or a parameter. `SequenceDocument` can't hold a timing track. Every later
phase either produces data these types can't express, or validates against rules these types can't
check.

### Tasks

**1a. Layout geometry**
1. Extend the `xlights_rgbeffects.xml` importer to read `parm1/parm2/parm3`, `StringType`,
   `WindowRows`, `WindowColumns`, and whatever else determines node count per model.
2. Add a normalized `Kind` enum (or at minimum a `ModelCategory`) derived from `DisplayAs`, rather
   than carrying the raw string — this is what drives resolution-aware effect legality later.
3. Capture full 2D/3D position and bounding geometry, not just a single `Point2`.
4. Enumerate submodels as first-class addressable targets (megatree slices, matrix regions, face
   parts), not just a reference shape inside a group member list.
5. Build and unit-test a verified pixel table per model, cross-checked against the XML's own node
   count attributes — this is the artifact the coverage ladder (architecture §7) depends on entirely.

**1b. The effect recipe system**
6. Design a real `IEffectRecipe` abstraction (or equivalent) that can carry: parameters (typed, not a
   bare string dictionary), a palette reference, layer/z-order, blend mode, transitions, and value
   curves — not just `(recipeId, ModelId, startTicks, endTicks)`.
7. Defer the actual recipe *catalog* to Phase 2 (it's generated from xLights metadata) — here, build
   only the shape the catalog will plug into, plus a registration mechanism that doesn't require
   edits in three coupled files per recipe.

**1c. The intermediate representation**
8. Extend `SequenceDocument` (or design its successor) to hold: a palette table, timing tracks as
   first-class content (architecture §6), per-effect settings matching the new recipe shape, blend
   modes, transitions, and sequence metadata (`author`, `song`, `mediaFile`, etc.).
9. Update `XsqExporter` to emit the richer IR: real timing-track `<Element type="timing">` blocks,
   multiple `<EffectLayer>` per element, the real `ColorPalettes` table, and the corrected header from
   Phase 0.
10. Re-run the Phase 0 round-trip test against the new exporter with a hand-built multi-layer,
    multi-timing-track IR to confirm it still imports cleanly.

### Depends on
Phase 0 (exporter ground truth must be known before extending the exporter further).

### Acceptance criteria
- A hand-authored `SequenceDocument` with 2+ layers, a timing track, and a non-default palette
  round-trips through export and opens correctly in real xLights.
- Pixel table for a real `xlights_rgbeffects.xml` (e.g. the `C:\xLights` show) matches hand-computed
  totals from `NodesPerString`/`NumArches × NodesPerArch`.
- Adding a new effect recipe requires touching one place, not three.

## Phase 2 — Knowledge: effect vocabulary and corpus mining

**Why here.** This phase has no dependency on rendering or the IR being finished — it's pure data
extraction — but its output (the generated effect schema, the pattern library, the craft rules) feeds
directly into Phase 1's recipe catalog and every LLM-facing phase after it. Running it in parallel
with late Phase 1 work is reasonable if capacity allows; it's listed after Phase 1 only because the
recipe *catalog* (not the recipe *shape*) depends on its output.

### Tasks

**2a. Effect vocabulary (architecture §8a)**
1. Write a generator that parses xLights' `resources/effectmetadata/<Effect>.json` (all 56 effects)
   plus the shared `Buffer.json`/`Blending.json`/`Color.json` panels into a structured schema: effect
   name, property ids, control types, defaults, ranges, choice enumerations, `valueCurve` capability.
2. Generate a JSON Schema (or equivalent) from that for constraining LLM output in later phases.
3. Generate a validator that checks a proposed setting against real parameter names, ranges, and
   value-curve eligibility.
4. Implement the serialization rules verified in architecture §8a: alphabetical key sort, default
   omission, `&comma;` escaping, `E_TEXTCTRL` vs `E_SLIDER` by divisor, `T_` authority over `B_` for
   `LayerMethod`, bare `SLIDER_` exceptions.
5. Wire this generated catalog into Phase 1's `IEffectRecipe` registration mechanism.

**2b. Corpus mining (architecture §8b)**
6. Audit the 31 sequences in `C:\xLights`: which have usable paired audio, which are licensable for
   mining (user-authored and OSS-licensed only — see architecture §8b licensing section; exclude paid
   vendor sequences from any mined statistics that might ship).
7. Build a parser that aligns each `.xsq`'s effects onto its song's beat grid (reusing the analysis
   pipeline from `XlightsAI.Studio.Rhythm`/`.Structure`).
8. Produce the `PatternLibrary`: effect frequency by geometry/energy, density curves by section kind,
   layer-count and blend-mode distributions, palette-size statistics, Mode A vs. Mode B emission
   ratios.
9. Build the `ExemplarIndex`: section-level fingerprints (tempo, energy percentile, band balance,
   vocal activity, section kind) with retrieval by similarity.
10. Implement the CraftRules induction+verification loop: propose candidate rules from an aligned
    exemplar, check each against all mineable sequences, promote only rules clearing a coverage/
    confidence threshold — into both prompt content and, where applicable, a deterministic validator.
11. Encode the one rule already concrete enough to skip induction — the 2/2/4 eight-bar pattern
    (architecture §8b) — directly as a Look variation schedule.

### Depends on
Phase 1's recipe shape (for 2a.5). The rest of Phase 2 can start in parallel with late Phase 1.

### Acceptance criteria
- Every one of xLights' 56 effects has a generated, validated parameter schema; an invalid parameter
  name or out-of-range value is rejected before it reaches the exporter.
- The corpus-wide effect vocabulary tally (architecture §8b) is reproducible from code, not
  hand-copied.
- At least 3 CraftRules have been induced, verified against the corpus, and promoted — demonstrating
  the pipeline works end-to-end on real data.

## Phase 3 — Analysis extensions

**Why here.** These are the four specific L0 extensions architecture §12 calls out as blockers for
later creative quality (per-band energy, vocal activity, measured phrase period, cadence-aware
phrasing). They're independent of the IR/recipe work and can proceed in parallel with Phase 2, but
Phase 4 (the constraint engine) and Phase 5 (the Show Bible) both consume their output, so they must
land before those.

### Tasks

1. **Per-band energy**: expose bass/mid/high spectral-flux-derived energy as first-class analysis
   output (it currently lives trapped inside `OnsetDetector`). This feeds frequency-split prop
   routing and labelled timing tracks (kick/snare/hat).
2. **Vocal activity**: derive a `vocalActive` envelope from the existing two-stem separation
   (vocals + accompaniment), despite the six-member `StemKind` enum only populating two in practice.
3. **Measured phrase period**: replace `PhraseSegmenter.TargetPhraseLengthBars: 8` with a statistical
   fit per song (the methodology is already written up in `C:\xLights\MUSIC_FLOW_ANALYSIS.md` — same
   binomial significance test against 4-bar vs. 8-bar grids).
4. **Cadence-aware phrasing fix**: resolve the hash mismatch where `StructureAnalysisRunner` passes
   `MelodyTrack: null` into `PhraseSegmenter` because the melody's `SourceAssetHash` is the lead
   stem's hash rather than the song's. Thread the correct hash through.
5. **(Stretch, needed for Phase 8 singing faces)**: phoneme alignment from the vocals stem — scope
   this as its own spike if it looks large; it can land after Phase 7 if needed, since singing faces
   are a style feature, not a core-path blocker.

### Depends on
Nothing from Phase 0–2. Can run in parallel with them.

### Acceptance criteria
- Per-band energy is queryable per time window and visibly differentiates a bass-heavy section from a
  treble-heavy one on a known test track.
- Phrase period is measured, not hardcoded, and reproduces the `MUSIC_FLOW_ANALYSIS.md` result (4-bar
  significant at p=0.0039, 8-bar not significant) on the reference track.
- `vocalActive` correctly flags the known vocal-cluster timestamps from `EXPORT_AUDIT.md`'s vocals
  investigation (~94s, ~400–412s, etc.) on that same track.

## Phase 4 — The deterministic constraint engine (L4) and emission strategy

**Why here.** This is the compiler at the heart of the design (architecture §6–§7) — it has to exist
and be independently correct *before* any LLM output is plugged into it, because the LLM's output is
only as trustworthy as the thing enforcing its constraints. Building this against hand-authored test
Looks (not LLM output) lets it be verified in isolation.

### Tasks

1. **Grid correctness**: beat-index bar definition, measured phrase quantization (consumes Phase 3),
   frame-interval-aligned boundaries, note-value fade durations.
2. **The always-moving rule**: gap-splitting pass that loops until no gap survives, with a rotating
   ≥6-state filler pool.
3. **Pixel-weighted coverage**: the monotone coverage ladder, individually addressable pixel-heavy
   props, duty-cycle correction table per effect family, Helmholtz–Kohlrausch per-hue brightness
   normalization.
4. **Compositional legality checks**: resolution-aware effect/prop matching, transition capability
   matrix enforcement, hue-family-per-frame limits, per-model effect stagger without palette stagger,
   easing-on-every-ramp enforcement, intentional-vs-accidental darkness (declared negative space only).
5. **Mode A/B emission strategy**: implement the "prefer one long effect bound to a labelled timing
   track" rule (architecture §6) with Mode B (discrete per-event effects) as the fallback for effect
   types with no timing-track input. This includes emitting the timing tracks themselves
   (`Beats`, `Bars`, `Phrases`, `Sections`, and labelled `Percussion` once Phase 3's per-band energy
   lands).
6. **Unit discipline**: typed `BarIndex`/`BeatIndex`/`Ticks` throughout, explicit key threading (the
   architecture doc flags a real historical bug class here — don't reintroduce it).
7. **A `Look` → `ChoreographyIR` compiler**: given a hand-authored `Look` (architecture §4) and a
   section's music data, expand it into the IR — this is the component Phase 6's LLM output will
   eventually drive, but it must work standalone first.

### Depends on
Phase 1 (IR, recipe shape), Phase 2 (effect vocabulary for validation), Phase 3 (per-band energy,
measured phrase period).

### Acceptance criteria
- Feed the compiler a hand-authored Look library (3–5 Looks) against a real song + layout and it
  produces a valid `.xsq` that passes every rule in architecture §7 as an automated test, with no LLM
  involved.
- The always-moving rule holds on the output (max gap ≤ 1 bar) for a full song.
- Pixel coverage ladder is monotone and matches hand-computed expectations for at least 3 energy
  levels.
- Re-run the `C:\xLights` reference track through this compiler and compare its metric battery
  (architecture §9 table) against the hand-sequenced reference — this is the first point the new
  pipeline can be honestly compared to prior manual work.

## Phase 5 — The Show Bible (L2, Director)

**Why here.** This is the first LLM-facing phase, and it depends on everything that makes its output
trustworthy: the compiler to consume it (Phase 4), the knowledge to ground it (Phase 2), and the
provider abstraction to call it with.

### Tasks

1. **Provider abstraction**: build or extend the existing `XlightsAI.Studio.AiEdits` plumbing
   (BYOK credential store, retry/backoff, size caps) into a role-based interface supporting Director/
   Choreographer/Critic roles independently configurable per architecture §14. Reuse the DPAPI
   credential store and structured-output deserialization discipline already present.
2. **Show Bible schema**: a flat, shallow, reviewable schema for palette set (with functional roles),
   prop roles, the Look library, the energy arc, peak moments, signature gestures, and the
   withholding plan — per architecture §5. Keep it small enough that a human can read the whole thing.
3. **Prompt construction**: assemble the Director prompt from MusicModel (Phase 3 output), Layout
   (Phase 1 geometry), style selection, and retrieved exemplars (Phase 2's `ExemplarIndex`) with the
   effect vocabulary and craft rules as cached context.
4. **Prompt caching discipline**: structure the prompt so the large stable prefix (effect vocabulary,
   craft rules, exemplars) precedes the small per-song volatile content, and instrument
   `cache_read_input_tokens` to catch silent invalidation.
5. **Validation**: every Look in the returned Show Bible must validate against Phase 2's generated
   effect schema before being accepted — reject and retry on schema violations rather than silently
   coercing.
6. **Storage**: persist the Show Bible as a diffable artifact under the project's `bible/` directory
   (architecture §13), following the existing atomic JSON-store pattern.

### Depends on
Phase 1 (geometry for prop-role assignment), Phase 2 (vocabulary + exemplars), Phase 3 (music model
inputs), Phase 4 (something must eventually consume this — build order-only dependency, not a hard
blocker for writing the Director itself).

### Acceptance criteria
- Given a real song and the `C:\xLights` layout, the Director produces a Show Bible with 8–20 Looks,
  a 3–5 palette set with functional role assignments, and a per-section energy arc — and every Look
  validates against the Phase 2 schema on the first attempt for a strong majority of generations.
- A human can read the full Show Bible and understand the intended show without seeing a single frame.
- Repeating the same call twice with prompt caching enabled shows non-zero `cache_read_input_tokens`
  on the second call.

## Phase 6 — Per-section choreography (L3)

**Why here.** This is the cheap, parallel, high-volume LLM layer that turns the Show Bible into
per-section scripts the Phase 4 compiler can expand. It depends on the Show Bible existing and the
compiler being able to consume Look references.

### Tasks

1. **SectionScript schema**: minimal per-section output — which Look, which variation, how events
   bind to specific props/groups for that section — kept flat per the structured-decoding reasoning
   tax (architecture §2).
2. **Batching**: issue the ~30 per-section calls via the provider's Batch API (architecture §14) where
   available, sharing the cached Show Bible + vocabulary + craft-rules prefix.
3. **Wire Phase 4's `Look → ChoreographyIR` compiler** to consume `SectionScript` + `Look` instead of
   a hand-authored Look directly.
4. **End-to-end first full generation**: song + layout → Show Bible → per-section scripts → compiled
   IR → exported `.xsq`, with no render/critique loop yet (that's Phase 7). This is the first point a
   complete LLM-driven sequence exists.

### Depends on
Phase 4 (compiler), Phase 5 (Show Bible + provider abstraction).

### Acceptance criteria
- A full song generates end-to-end to a valid, importable `.xsq` with no manual intervention.
- The generated file's structural stats (effect count, layer count, palette count, effect-type
  diversity, timing-track count) land within an order of magnitude of the corpus range — not the
  current 100×-below-corpus placeholder output.
- Cost per generation is measured and logged (architecture §13's `llm/` call log) for at least 5 real
  songs, to calibrate the "a few dollars per song" target before building the more expensive Phase 7
  loop on top.

## Phase 7 — The harness: render, measure, critique, revise (L5/L6)

**Why here, and why it's the biggest phase.** This is what turns "a complete sequence" into "a good
one," and it's explicitly the piece already proven to work manually (the `RENDER_CRITIQUE.md` /
`EXPORT_AUDIT.md` loop). It depends on Phase 0's render-automation decision and Phase 6 producing
something to critique.

### Tasks

**7a. Render (shape depends on the Phase 0 decision)**
1. If headless rendering is viable: build the automated render pipeline producing FSEQ/frames per
   iteration, extending `XlightsAI.Studio.Rendering`.
2. If not: implement the `.xsq`-derived prediction fallback, clearly flagged as lower-fidelity per
   architecture §9, and scope down the visual-critique channel accordingly.

**7b. Measure**
3. Implement the full metric battery from architecture §9's table, mapped onto the existing
   `XlightsAI.Studio.Refinement` types (`MetricValue`, `QualityReport`, hard gates).
4. Validate the battery against the Phase 4 standalone-compiler output from the reference track
   comparison, to confirm metrics correctly flag the historical defects documented in
   `EXPORT_AUDIT.md` (brightness/drop regression, red-snap-not-red, matrix desaturation, build
   non-escalation) when deliberately reproduced.

**7c. Critique**
5. Numeric critique: mechanical, every iteration, grounded only in measured properties.
6. Visual critique: frame extraction at section boundaries/peaks + a vision-model call carrying the
   Show Bible's stated intent for that section — a different model family from the Director, per
   architecture §9's bias mitigation.
7. Judging discipline: pairwise comparison (not absolute scoring), randomized order run both ways,
   explicit low confidence calibration (don't assume chain-of-thought helps here).

**7d. Revise**
8. `RevisionDirective` schema targeting specific sections.
9. Wire directives back into Phase 6 to re-run only affected `SectionScript`s, leaving the Show Bible
   untouched unless a directive specifically targets it.
10. Bounded candidate search: small N (4–8) best-of-N with a diverse scorer, never unbounded.
11. Convergence discipline: full battery re-run and diffed every iteration against the *previous*
    iteration (not just targets); keep all iteration artifacts; select best-scoring, not last.

### Depends on
Phase 0 (render strategy decision), Phase 6 (something to critique).

### Acceptance criteria
- Running the loop on a real song for 3+ iterations shows the metric battery trending toward targets
  without an undetected regression (i.e., the convergence-discipline diff check actually catches at
  least one regression during testing, proving it works).
- The visual critique catches at least one defect class the numeric battery alone would have missed
  (replicate the "red snap doesn't read as red" scenario deliberately to confirm).
- Iteration cost is bounded and logged; a showcase-tier run on a real song completes within whatever
  cost ceiling is set for that tier.

## Phase 8 — Style system and secondary craft features

**Why here.** These sit on top of a working core loop and are additive rather than blocking —
shipping the core pipeline without them produces a working but less differentiated product. Order
within this phase is flexible.

### Tasks

1. Implement the style preset taxonomy (architecture §10) as structured bundles: palette discipline,
   effect pool, density curve, prop-role bias — each conditioning the Director prompt and the metric
   battery's target bands.
2. Wire `vocalActive` (Phase 3) into hold-vs-chase gating in the compiler.
3. Singing-face support: phoneme alignment (deferred from Phase 3 if not done there), the three-level
   lyric timing track, and the `Faces`/`Text_LyricTrack` effect wiring.
4. Show-length guidance (10–15 minute target) surfaced in the Director's planning.

### Depends on
Phase 4 (compiler), Phase 5 (Director prompt structure), Phase 3 stretch item (phoneme alignment).

### Acceptance criteria
- At least 2 style presets produce visibly and measurably different output (different effect pools,
  density curves, palette constraints) on the same song.
- A song with lyrics and a face-capable model produces a working `Faces` effect bound to a real
  phoneme timing track.

## Phase 9 — Verification, regression, and productionization

**Why last.** These are the mechanisms that keep quality from silently regressing once the system is
in real use, and the human-preference confirmation that nothing earlier in this plan can substitute
for.

### Tasks

1. **Regression suite**: fix a set of songs × layouts × styles, regenerate on every change, track
   metrics over time (architecture §16 level 4).
2. **Blind pairwise trials**: wire the existing `XlightsAI.Studio.Release` `BlindTrial`/
   `AestheticRating` machinery to compare generated vs. corpus sequences on the same song/layout.
3. **Tiering**: draft (single pass) / standard (one critique iteration) / showcase (bounded search +
   multiple iterations), each with a shown cost estimate before running.
4. **Real-world verification**: render a generated sequence against the actual `C:\xLights` house and
   watch it — this is the verification level the project has never yet reached, per its own changelog.
5. Close out the disclosed limitations this plan resolves (the exporter placeholder warning, the
   missing vocal discrimination, the hardcoded 8-bar phrase assumption) in `CHANGELOG.md`.

### Depends on
Phase 7 (loop must exist to compare against corpus), Phase 8 (styles should be in place for a
representative regression set).

### Acceptance criteria
- A blind pairwise trial run with a real evaluator shows the generated sequence preferred at a rate
  meaningfully above chance against at least one corpus sequence on a comparable song.
- The regression suite catches a deliberately introduced regression in CI before it would reach a
  release.
- A generated sequence has been watched running on the real house, not just verified structurally.

Phase 1 (geometry/recipe/IR) ──┼─→ Phase 4 (constraint engine) │
                                │        ↑                     │
Phase 2 (knowledge) ───────────┤        │                     │
                                │        │                     │
Phase 3 (analysis ext.) ───────┘        │                     │
                                         ↓                     │
                              Phase 5 (Show Bible) ────────────┘
                                         ↓
                              Phase 6 (per-section choreography)
                                         ↓
                              Phase 7 (render/measure/critique/revise)
                                         ↓
                        ┌────────────────┴────────────────┐
                        ↓                                  ↓

strict chain — each phase's acceptance criteria are the real gate for starting the next.
